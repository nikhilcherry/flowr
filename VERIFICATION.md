No corruption, no duplicate execution.

## 8. `gc`

- `--older-than 7d --dry-run` immediately after a run: reports 0 objects
  deletable (everything is reachable from the just-finished run); real gc
  changes nothing; a subsequent run is still 100% HIT.
- Artificially aging the store's only run past the cutoff: dry-run and real
  gc agree exactly (62 objects / 87.2 kB), and the underlying
  `collect_garbage()` API returns an exact byte count (`freed_bytes: 89280`)
  — the displayed "kB" is a base-1024 conversion (i.e. technically KiB),
  a cosmetic label shared with plenty of other CLIs, not a counting bug.

**Note on `--older-than 0d`:** a duration of exactly zero can never protect
a *completed* run under exact-timestamp semantics, because some nonzero
wall-clock time always elapses between a run finishing and `gc` running
afterward — there's no timestamp that satisfies `started_at >= now`. This
is expected behavior, not a defect: `tests/test_gc_dry_run_then_delete`
depends on exact-timestamp aging to prove a fully-stale store is fully
reclaimable, which an "always protect the latest run" rule would break.
Use a real window (`--older-than 1h`, `7d`, etc.) — `0d` is not a
meaningful "keep nothing new" cutoff, it's a "nothing is ever new enough"
cutoff.
